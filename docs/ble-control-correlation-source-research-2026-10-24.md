# App-independent long-term local BLE control: capability/state correlation

Research date: 2026-10-24. Scope: source inspection and offline inspection of existing captures only. No hardware, BLE connection, SSH, device-network access, or cloud-account access was used. Public GitHub repositories were fetched over the Internet and their checked-out commits inspected. Only this document is added to the project.

## Conclusions

Local control can survive loss of the phone app and service for the implemented plaintext and encrypted families **if the protocol implementation, revision-specific profiles, effect payloads and any required authorization secret have been preserved**. A readable light is not a self-describing device. Advertisement identity/pact, firmware/hardware and current mode narrow the command dialect; counts and colour pages constrain topology. They do not enumerate every feature, reconstruct an uploaded effect, supply physical layout, or guarantee recovery after a factory reset. This is an inference from the independent command, profile, scene-store and authorization implementations cited below.

Use four separate evidence levels throughout:

- **Capture:** bytes from an identified device/session, including this repo's committed bench evidence. A write/read match proves stored wire state; physical output requires a separate observation.
- **Source:** an executable implementation or its author's app/firmware reverse engineering. A synthetic regression test establishes implementation behavior, not hardware qualification.
- **Inference:** a proposed correlation or implementation priority deduced from those sources.
- **Unknown:** absent evidence; silence and zero-filled records are not negative capability declarations.

## 1. Identity and readable state select a candidate dialect

**Source.** The app's dispatch chain is advertised SKU → compiled goodsType/family registry → supported pact route, with firmware/hardware gates. Its feature tables are compiled per family rather than downloaded as a universal cloud capability profile. The manufacturer-data flags include encryption and broadcast version, alongside pact type/code. Preserve original AD structures and the scanner's manufacturer-data representation: byte offsets differ when the BLE framework has already removed the company identifier. [B protocol §§18–19](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/spec/docs/GOVEE_BLE_GATT_PROTOCOL.md#18-device-identification-protocol-selection--pairing), [H advertisement parser](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/custom_components/ha_govee_led_ble/advertisement.py).

**Capture in R.** H6159 firmware 1.07.02 reports colour mode `0x02`; H6181 firmware 2.03.11 reports `0x0D`, contradicting the earlier same-family table assumption. The additional bench fixtures contain raw power, brightness, mode and ACK frames with source timestamps. For example, H6159 mode `aa0502d6e2ff0000000000000000000000000066` carries RGB 214/226/255. This establishes that revision's observed mode, not support for every command variant. The census-only firmware report deliberately labels reads as inferred; the separate controlled writes provide stronger evidence. [R bench fixtures](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/docs/bench-evidence/2026-10-23-additional/fixtures.json), [R provenance and limits](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/docs/bench-evidence/2026-10-23-additional/README.md), [R census report](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/docs/bench-evidence/2026-10-23-firmware/report.md).

**Source counterexample to SKU-only selection.** H6199 pact 1/1 uses an app-derived legacy `0x0B` RGB writer and brightness register mapping 20–254. The historical upstream explicitly calls those writes candidates awaiting independent official-app capture/owner qualification; it disables scenes/music/video/uploads and does not claim brightness/colour readback. Current H retains that partial profile. Hardware version alone does not identify pact. [H-old pact restriction](https://github.com/teh-hippo/ha-govee-led-ble/blob/b2cd788226682c7405ffa0816d3a8d9e71d97ab1/docs/h6199-pact1.md), [H profiles](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/custom_components/ha_govee_led_ble/const.py).

**Inference.** Resolve a profile from the whole identity tuple, record why it was selected, then retain observations separately from defaults. A plain-colour `AA 05` reply is useful evidence for a colour submode. A scene/music/video reply identifies the current mode, not the static-colour writer. Even `0x15` does not uniquely identify field layout, mask width or feature set. Brightness values ≤100 alone cannot distinguish percent from a 0–255 register. R's submode→brightness-scale mapping is a model heuristic supported on named revisions, not a capability field returned by firmware. [R probe](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/custom_components/govee_bluetooth/probe.py), [B profile resolution](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/devices/_resolve.py).

**Correction to older notes.** Current B documents `AA EF` as a read-only pact report, not negotiation: firmware-derived examples include constant reports and a non-answering H6008. This does not make it a universal feature-discovery command. Likewise, “only live capability read is `0x40`” describes the app's main IC-driven route, not every readable topology field: H6062 has a mandatory `AA 41` section-count path. [B protocol §18.4](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/spec/docs/GOVEE_BLE_GATT_PROTOCOL.md), [B profile count semantics](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/devices/profile.py).

## 2. Counts, masks and topology are different facts

**Source.** `AA 40` can provide IC/segment information, but interpretation is family-specific. Current B derives H6641 colour-piece count using `ceil(clamped IC/5)`; other goodsTypes use other divisors. Its direct colour-read path does not use the reply's third byte. Static families use profile counts. H6062 instead uses `AA 41` sectionNum for masks, index bounds and colour-page walks. Readback piece counts can differ from write/addressable counts. [B profile](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/devices/profile.py), [B readback implementation](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/devices/_readback.py), [B protocol §18.6](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/spec/docs/GOVEE_BLE_GATT_PROTOCOL.md).

**Source.** `AA A5 <group>` is not one universal record grammar. B distinguishes four-record direct groups from three-record V2 batches; H6199's schema specifies 4+4+4+3 records and retains opaque bytes. `AA 05` on segmented devices can omit RGB; H-old's H6199 investigation reports no Kelvin in either mode-query variant. Therefore do not decode absent fields as black, zero Kelvin, or a confirmed colour clear. [B profile](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/devices/profile.py), [H H6199 reply schema](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/tools/ble/kaitai/h6199_status_reply.ksy), [H-old capture findings](https://github.com/teh-hippo/ha-govee-led-ble/blob/b2cd788226682c7405ffa0816d3a8d9e71d97ab1/docs/h6199-support-findings.md).

**Inference.** Keep separate fields for physical IC count, addressable colour pieces, write mask, readback grouping and named zones. A contiguous n-bit mask `(1 << n) - 1` is valid only after the selected writer and count semantics are known. R currently hardcodes `FF 7F` for its `0x15` whole-strip writer; that is not universal whole-device coverage. H has masks of several widths; B also constrains per-segment brightness to groups and some CCT selections to complete zones. Count does not reveal which bit is physically left/right, the ring/panel division, strip orientation, camera geometry, or cut/splicing layout. Those need source-defined mappings or separately preserved physical observations. [R writer](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/custom_components/govee_bluetooth/protocol.py), [H masks](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/custom_components/ha_govee_led_ble/const.py), [B grouping constraints](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/devices/profile.py).

## 3. Scenes and DIY: selectors do not contain the program

**Source.** A scene mode report/activation code is distinct from an uploaded effect. B's scene store includes names, codes, base64 params, scene type, command version and scene-set variants. Its planner selects different upload paths by family and scene-version gates, including legacy `A3`, H60A6 dialect B and MTU-dependent `A4`. Some entries are bare activations; some are placeholders whose real effect blob requires authenticated resolution. Consequently an offline scene catalogue must contain the resolved payload and upload metadata, not only names/codes or parameter IDs. [B scene implementation](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/scenes/__init__.py), [B bundled store](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/scenes/store.json), [B upload research](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/spec/docs/SCENE_UPLOAD_ENCODING.md).

**Inference.** `AA 05 04 <code>` can correlate a current selection with a preserved catalogue. `AA 05 0A <code>` can identify a DIY slot. Neither is evidence that its program can be read back, restored after replacement, or regenerated from code. Do not infer upload residency after power loss/reset from an echoed selector. Preserve the authored DIY representation, decoded upload body, exact framing/activation recipe and any unknown bytes together. A stored selector or successful ACK is insufficient evidence of visible playback; R's protocol notes record H6006 accepting/reporting legacy scene IDs without visible execution. [B upload research](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/spec/docs/SCENE_UPLOAD_ENCODING.md), [R H6006 findings §14.1](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/docs/govee-ble-protocol.md).

## 4. Music and video: local engines versus external inputs

**Source.** Music is family-specific. The H617A investigation traces new music selectors that report only mode/sensitivity; palette/background/style reside in an `A3` subtype `41` companion body restored by the app from local storage, without a demonstrated full BLE-read endpoint. Current H tests explicitly identify themselves as APK/contract regressions, and its command preparation compiles parameter uploads separately from selectors. Thus a selector-only sensitivity edit and re-uploading a complete preset have different preservation requirements. [H-old music findings R6](https://github.com/teh-hippo/ha-govee-led-ble/blob/b2cd788226682c7405ffa0816d3a8d9e71d97ab1/docs/h617a-support-findings.md), [H command preparation](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/custom_components/ha_govee_led_ble/music_commands.py), [H tests and qualification limits](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/tests/test_h617a_music.py).

**Source.** Phone-microphone music also has a separate seven-byte `A5 02 83 RGB checksum` stream with additive checksum. It must not be confused with the `AA A5` status-page query or ordinary 20-byte XOR frames. App independence for that mode requires another program to supply its input stream; selecting the mode alone does not replace the phone microphone. Whether a specific mode uses an onboard microphone must come from that family's source/capture. [H stream schema](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/tools/ble/kaitai/music_stream.ksy).

**Source/inference.** H6199 video has model-specific source/region/saturation/sound/softness/brightness fields, plus separate white balance and blank-screen settings. Read and write layouts are separately specified: a status payload is not automatically a replayable command body. A controller can potentially select a device's existing camera/HDMI engine locally; readable mode does not reconstruct the image stream, camera calibration or external HDMI input. The schema explicitly marks some direction/position/DIY additions as speculative app/register evidence rather than official-app captures. Preserve that qualification instead of presenting every schema field as verified. [H video writer](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/tools/ble/kaitai/h6199_command_write.ksy), [H video/settings reader](https://github.com/teh-hippo/ha-govee-led-ble/blob/50ab40c9e25b1710b9dded9b94eea9991e4b364d/tools/ble/kaitai/h6199_status_reply.ksy).

## 5. Encryption and pairing: separate offline prerequisites

**Source/capture.** Plaintext, encrypted sessions and per-device authorization are separate mechanisms. V1 uses the public fixed PSK, `E7 01` session-key reply and `E7 02` confirmation; later frames use AES-ECB plus RC4 with the session key. E publishes H600B handshake/control replay material; R has corresponding known-answer fixtures. Those establish an offline implementation route for the demonstrated family without the phone app. They do not make an old session key reusable across reconnects or prove every encrypted model uses V1. [B handshake](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/transport/handshake.py), [B cipher](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/crypto.py), [E captured replay](https://github.com/egold555/Govee-Reverse-Engineering/blob/900b003174f5ecd6708b3d5266ea0514926aefa1/Products/H600B/utils.py), [R cipher fixtures](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/tests/test_cipher.py).

**Source.** L's H1270 V2 implementation uses static handshake/derivation keys, device identity from the handshake, exchanged eight-byte IV prefixes and AES-GCM with packet counters. It identifies encryption version in `2b12` byte 1 on that device, unlike the byte-0 app rule in older notes. Preserve raw BGC bytes and the decoder rule, not merely a Boolean “encrypted”. This implementation plus known-answer tests supports offline feasibility for that demonstrated exchange, not arbitrary future firmware or every `ctlchannel` family. [L implementation](https://github.com/lasswellt/govee-homeassistant/blob/40d5bd8b43f7008ab4db5471177facb3eb847510/custom_components/govee/api/ble_crypto.py), [L tests](https://github.com/lasswellt/govee-homeassistant/blob/40d5bd8b43f7008ab4db5471177facb3eb847510/tests/test_ble_crypto.py).

**Source and limit.** The eight-byte `B1/B2` authorization secret is not the wire cipher's PSK. App sources describe local cache/account storage; B's H5083 firmware specification documents retrieval inside a five-second physical-button window even in previously paired states. That corrects an overly general “unbound only” interpretation, but H5083 is a plug: no evidence here establishes that every light has this route. Its simulator's random-byte abstraction does not prove actual firmware entropy. R's H7135 derivation research is also model/image-specific and cannot establish a light bypass. [B secret architecture](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/spec/docs/GOVEE_BLE_GATT_PROTOCOL.md), [B firmware specification](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/spec/firmware.yaml), [R pairing-source limits](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/docs/pairing-secret-research-sources.md).

**Inference.** Already possessing a valid persistent secret may remove a runtime account dependency; losing it may prevent offline recovery on an enforcing revision. A family tag alone does not prove enforcement, and silence alone does not prove a lock: wrong write procedure, channel, readiness, cipher or dialect can look identical. R's bench records include first-read timing failures and write-property evidence. No claim is made here that factory reset preserves secrets, that all unpaired lights can be provisioned offline, or that state readback yields authorization credentials. [R mechanism matrix](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/docs/encrypted-protocol-matrix.md), [R bench limits](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/docs/bench-evidence/2026-10-23-additional/README.md).

## 6. Practical priorities for this repo

These are recommendations inferred from the cited implementations, not changes made by this research.

1. **Preserve identity and evidence first.** Keep raw advertisements, GATT UUIDs/properties, BGC bytes, model/pact/hardware/firmware and timestamps. Key profiles by revision evidence; retain overrides and conflicts. Separate read observation, ACK acceptance, matching write/read verification and visible-output observation.
2. **Deepen readback before broad effect support.** Add family-qualified colour-page grammars, section/IC count interpretation and bounded page walks. Keep unknown fields/raw replies. Do not use R's generic four-record parser or 15-bit writer as a universal RGBIC contract. Preserve selector matching and distinguish ACKs from state.
3. **Treat restoration as its own capability.** Preserve every relevant white-balance flag, mode parameter and unknown byte. For uploaded DIY/music, require a saved complete payload to claim exact restoration; otherwise label it incomplete. Readable power/RGB alone is not a complete backup.
4. **Build an offline effect bundle.** Include resolved scene blobs, version filters, family upload dialects, decoded DIY/music bodies, order/ACK rules, negotiated-MTU framing and activation codes. Explicitly mark unresolved placeholders unavailable offline. Do not assume a selector enumerates or exports resident content.
5. **Qualify security independently.** Maintain plaintext/V1/V2/session-auth distinctions and known-answer vectors. Keep persistent secrets in private backups. Track offline provisioning and post-reset recovery as unknown until model-specific evidence exists.
6. **Test offline with existing material.** Replay committed frames through pure parsers/ciphers and validate lengths/checksums/selector correlation; use synthetic tests only for software contracts. Future hardware work belongs in a separately authorized task and must record physical outcomes separately from wire echoes.

Implementation bases: [R protocol/parser](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/custom_components/govee_bluetooth/protocol.py), [R probe](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/custom_components/govee_bluetooth/probe.py), [B profile constraints](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/devices/profile.py), [B scene planner](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/scenes/__init__.py).

## 7. Offline preservation package

**Recommended archive:** source Git bundles at the pins above; licenses; schemas and generated readers; reproducible dependency versions and install artifacts; profile tables and explanation of their gates; captured raw/decrypted frames and deterministic vectors; resolved scene store and authored DIY/music bodies; topology/orientation/calibration notes; firmware/hardware history; and any legitimately obtained firmware/app splits with hashes and provenance. A base APK alone can omit the on-demand `pact_*` code containing the device-specific writer. Firmware binaries and APK splits are not supplied by every public source repository; archive availability must be checked rather than inferred from a specification citing a local decompile. [B split-module research](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/spec/docs/GOVEE_BLE_GATT_PROTOCOL.md), [R artifact availability investigation](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/docs/pairing-secret-research-sources.md).

Maintain a manifest with SHA-256, original location, acquisition date, source commit, model/revision, evidence level and whether a record is redacted. Keep a **private recoverable archive** separate from shareable evidence: a redacted `B1/B2` log cannot restore a secret; V1 handshake material can reveal session keys under the public PSK; identifiers and account exports need not be public. Never describe a scrubbed or reconstructed frame as original wire bytes. [R redaction implementation](https://github.com/Mezzle/govee-bluetooth/blob/e69b84693dbaddfbf4abd3b38d27238fc1b887d7/custom_components/govee_bluetooth/protocol.py), [B handshake](https://github.com/Brady-Woods/govee-ble-local/blob/276b14b6b383b35ce931bbc2e7e6e81ca765d5f3/src/govee_ble_local/transport/handshake.py).

The final acceptance criterion for long-term independence is a reproducible installation and complete command/effect plan with network access disabled, using preserved inputs. Source inspection establishes feasibility and missing inputs; it cannot establish device behavior after a future firmware change, power loss or reset without corresponding device evidence.
